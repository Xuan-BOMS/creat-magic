# 轰界法术生成器实施方案

## 1. 产品定位

本项目应按“法术编译器”建设，而不是按“法术百科”或“元素技能树”建设。

核心产品判断：

```text
魔法是理解框架。
法术是可执行流程。
节点图是施法方案。
编译器负责判断方案能否成立。
```

用户在工作台中搭建节点链路，系统优先输出“是否成立、为何成立、为何失败”，再输出法术名称、叙述和卡片。任何文案生成都不得替代规则判断。

## 2. 已校准资料结论

资料来源以现有项目规划、世界观手册和字幕为准。第一版实现只抽取会影响规则内核的内容，不做全文知识库。

### 2.1 基础施法

- 法术由精神力引动环境中的魔力完成，真正持续消耗的是精神力、注意力和认知负荷。
- 普通法术基础流程为：开模、提纯、灌注、释放。
- 开模负责结构与容器，提纯负责现象倾向，灌注负责填入结构，释放负责触发、落点、方向和稳定。
- 每个步骤都有沉没成本。中断时已经投入的精神力不会自然返还。
- 法师需要安全环境、熟悉流程和必要时才施法的判断。

### 2.2 元素与理解深度

- 元素不是固定物质块，而是魔在不同激发方式下呈现的现象倾向。
- 火偏释放、升温、燃烧、扩散；水偏流动、液态、湿度、溶解；风偏运动、气压、气流、切割；土偏结构、固化、密度、承载。
- 以太不是简单第五自然元素，第一版可作为泛用干涉、矢量、振动、搬运、感知扩张的高认知负荷介质。
- 法术位阶代表理解深度、调度难度和复现能力，不直接等于伤害。

### 2.3 技巧与特殊体系

- 序列：多个法术如同一个法术，通过条件触发和肌肉记忆形成连锁。
- 多重：一个法术如同多个法术，核心代价是注意力并发，不等同于连续释放。
- 延迟：一个法术如同另一个法术，通过拉长或插入步骤积蓄效果，必须有维持方案。
- 结界：不是单纯护盾，而是条件工程。天时借气候，地利借地形，人和依靠诱因、转化、回填形成闭环。
- 祈愿：通过祈愿法阵向魔网发送请求，再链接神之遗物或知识碎片返还结果。风险来自未接收、部分接收、语义偏移、接口不兼容和代价失控。
- 附魔：把某种现象特性附加到对象上，必须校验对象是否适配该特性。
- 契约：条件绑定、代价绑定和违约后果绑定，必须存在接受窗口、灵魂或意识接口，以及清晰条款。
- 禁术：不是固定名单，而是治理判断。外部代价不可承受、自损过高、长期治理不可控，都可使方案被判为禁用或需授权。

## 3. 第一版目标

第一版只做可验证的规则内核和可用工作台，不追求覆盖全部轰界体系。

MVP 成功标准：

- 命令行或 API 能编译节点图。
- 至少支持普通、结界、祈愿三类链路。
- 能对失败图给出明确失败原因。
- 能输出法术卡、风险评分和优化建议。
- 前端能拖拽节点、连线、查看属性、编译、定位失败节点。
- 示例可稳定覆盖火球术、多重风刃、侦查结界、祈愿传送。

### 5.2 编译流程

第一版使用确定性管线，不上复杂规则 DSL。

```text
1. 载入节点库并校验版本
2. 解析图结构，检查孤点、环、非法边
3. 识别链路原型：普通 / 结界 / 祈愿 / 附魔 / 契约
4. 执行基础输入输出传播
5. 校验必需步骤和等效替代
6. 校验介质、操作、结构、载体兼容性
7. 校验施法者能力、场景条件和授权条件
8. 计算精神力、注意力、材料、维护和治理风险
9. 生成失败原因、警告、优化建议
10. 在规则通过或部分通过后生成法术卡
```

### 5.3 规则分层

基础拓扑规则：

- 图必须至少存在一个意图节点。
- 普通主动法术必须存在释放节点或等效外包载体。
- 弹体、刃、壁、场域等结构必须有开模或等效结构来源。
- 被标记为持续的法术必须有维持、延迟、循环、载体或外部供能方案。

介质与流程规则：

- 火适合提纯、灌注、扩散、压缩、附加，但高外溢。
- 风适合切割、机动、多重、扰动，但稳定性较低。
- 水适合防御、卸力、净化、束缚、渗透，但直接杀伤较弱。
- 土适合防护、构型、承载、封锁，但施法负担高。
- 以太适合感知、矢量、搬运、无属性干涉，但认知负荷高。
- 雷电适合传导、刺激、电磁、屏障和光道类接口，需校验载体导电与目标安全。

特殊体系规则：

- 祈愿必须有请求语义、法阵、魔网链接、代价和寄托物。
- 祈愿若缺少坐标、状态、方式、权限中的任意关键参数，传送类结果默认 unsafe。
- 结界必须存在天时、地利、人和至少一类成立条件。
- 人和结界必须存在诱因、转化、回填和循环闭合。
- 附魔必须校验被附加对象能否承载该特性。
- 契约必须校验条款、双方接受窗口、约束主体和违约后果。
- 禁术判断应输出治理标签，而不是直接删除结果。

### 5.4 评分模型

四项主评分：

```text
可执行性 executable
稳定性 stability
代价可承受性 cost
治理安全性 governance
```

评分只做解释性排序，不作为唯一判定来源。硬性缺失应直接产生 error。

建议初始权重：

- 缺少必需步骤：可执行性大幅下降。
- 介质与结构不兼容：可执行性下降，并给替代建议。
- 注意力并发过高：稳定性下降。
- 延迟无维持方案：稳定性和代价下降。
- 火、蒸汽、祈愿、体内施法、高位规则接口：治理安全性下降。
- 有魔法阵、卷轴、法杖、魔石等载体承担步骤时，实时精神力成本下降，但材料和载体风险上升。

### 5.5 法术卡输出

法术卡必须可追溯到图节点，不允许凭空扩写。

字段：

```text
名称
法术类型
施法目的
节点链路
施法流程
成立条件
代价
风险
失败场景
优化建议
治理标签
来源规则摘要
```

名称生成规则第一版用模板即可：

```text
介质 + 结构：火球、风刃、土墙
技巧 + 介质 + 结构：多重风刃、延迟火弹
功能 + 体系：侦查结界、封锁契约、祈愿传送
```

## 6. 节点库第一批

### 6.1 必做节点

介质：

- 火、水、风、土、以太、雷电

流程：

- 开模、提纯、灌注、释放、压缩、扩散、序列、多重、延迟、复合、附加、循环、结界循环、祈愿

结构：

- 弹体、刃、壁、场域、结界、附魔、契约

载体：

- 手势、咏唱、法杖、魔法阵、魔石、卷轴、寄托物

约束：

- 精神力、注意力、被打断、材料、环境、反噬、外溢、禁术、授权

接口：

- 魔网、神之遗物、祈愿法阵、灵魂接口、目标权限

### 6.2 数据原则

- 每个节点必须有输入、输出、成本、风险和兼容性。
- 每个节点必须有 `source_refs`，指向世界观手册或字幕标题。
- 节点库必须带版本号，编译结果记录使用的节点库版本。
- 第一版宁可节点少，也要每个节点能参与规则判断。

## 8. 前端工作台方案

第一屏直接进入工作台，不做营销式首页。

布局：

```text
顶部工具栏：项目名、节点库版本、编译按钮、保存按钮、示例菜单
左侧节点库：搜索、类型筛选、节点拖拽
中间画布：React Flow 节点图、连线反馈、错误高亮
右侧检查器：选中节点属性、输入输出、成本风险、兼容提示
底部结果区：编译状态、分数、失败原因、法术卡、优化建议
```

视觉原则：

- 风格应像“法术工程工作台”，不是卡牌游戏首页。
- 使用低饱和深浅对比，避免单一紫蓝或纯玄幻渐变。
- 节点按类型使用稳定色标和图标：意图、介质、流程、结构、载体、约束、接口各自区分。
- 操作按钮优先使用图标加 tooltip，例如编译、保存、撤销、重做、适配画布。
- 文案保持短句，避免在界面内解释产品功能。
- 卡片只用于节点、示例和结果块，不做卡套卡。
- 移动端第一版只保证可查看和基础编辑；复杂图编辑优先桌面体验。

关键交互：

- 拖节点到画布后自动创建实例。
- 连线时调用本地轻量校验，提示“可连接/不可连接原因”。
- 编译后错误节点高亮，点击错误定位节点。
- 示例菜单一键载入火球术、多重风刃、侦查结界、祈愿传送。
- 右侧检查器显示该节点的来源摘要，帮助用户理解世界观依据。
- 结果区区分 error、warning、unsafe、compiled，避免用户把高危当成功。

## 9. 示例验收图

### 9.1 火球术

链路：

```text
远程伤害 → 火 → 弹体 → 开模 → 提纯 → 灌注 → 释放 → 精神力/外溢校验
```

预期：

- status 为 compiled。
- 风险包含热场外溢、被打断、友军误伤。
- 优化建议包含法杖或咏唱提高稳定性。

### 9.2 多重风刃

链路：

```text
多目标切割 → 风 → 刃 → 开模 → 提纯 → 灌注 → 多重 → 释放 → 注意力校验
```

预期：

- status 为 compiled 或 partial，取决于施法者注意力参数。
- 低注意力施法者应得到并发不足错误或警告。
- 系统应说明多重不是连续释放。

### 9.3 侦查结界

链路：

```text
长期侦查 → 风/以太 → 环境条件 → 诱因 → 转化 → 回填 → 结界循环 → 子功能挂载 → 维护校验
```

预期：

- 缺少循环闭合时 failed。
- 循环成立时 compiled，但前期成本和维护要求高。
- 输出移动性弱、被破译后重建成本高。

### 9.4 祈愿传送

链路：

```text
移动 → 请求语义 → 祈愿法阵 → 魔网 → 神之遗物 → 寄托物 → 结果 → 歧义/反噬校验
```

预期：

- 缺少坐标、方式、目标状态、代价或寄托物时 unsafe。
- 参数完整时可 compiled，但治理安全性低。
- 输出语义偏移、接口不兼容、时间线副作用等风险。

## 10. 开发里程碑

### 阶段一：规则内核

目标：无前端也能编译节点图。

交付：

- 后端项目骨架。
- Pydantic 数据模型。
- YAML 节点库。
- 示例图 JSON。
- 编译器和规则校验。
- 风险评分和法术卡输出。
- 4 个示例测试。

验收命令：

```text
pytest
uvicorn app.main:app --reload
POST /api/compile
```

### 阶段二：Web 工作台

目标：用户可通过画布搭建并编译。

交付：

- Vite + React + TypeScript 前端。
- React Flow 画布。
- 节点库、检查器、编译结果面板。
- 示例载入。
- 本地草稿保存。

验收：

- Playwright 打开工作台。
- 载入四个示例，逐个编译。
- 检查错误高亮、结果面板、法术卡显示。
- 桌面和窄屏无明显遮挡、溢出和空白画布。

### 阶段三：项目保存与版本

目标：支持长期方案管理。

交付：

- SQLite 项目表、版本表。
- 保存、读取、版本快照。
- 节点库版本写入项目元数据。
- 示例模板库。

### 阶段四：知识扩展

目标：逐步加入轰界高阶体系。

优先顺序：

1. 附魔与附加体系。
2. 契约术。
3. 魔导具、魔法阵、魔石、卷轴。
4. 时间、空间、记忆、心灵等祈愿分支。
5. 死灵、德鲁伊、生体改造、信仰侧雷电与光道。

### 阶段五：部署

目标：服务器可访问、可维护、可备份。

交付：

- Docker Compose。
- Caddy 或 Nginx 反代。
- 管理员维护节点库。
- 数据备份脚本。
- 基础登录权限。

## 11. 验证策略

后端：

- 单元测试覆盖模型校验、节点加载、连接校验、评分、法术卡。
- 示例测试覆盖成功、失败、unsafe 三类结果。
- 每个特殊规则至少有一个负例。

前端：

- 类型检查和 lint。
- 组件级测试覆盖节点库、检查器、结果面板。
- Playwright 验证示例编译流程。
- 截图检查桌面和移动视口布局。

资料一致性：

- 节点库新增规则时必须附 `source_refs`。
- 高风险体系先写规则摘要，再加节点。
- 不直接从字幕自动生成规则，避免口播噪声进入核心判断。

## 12. 风险与取舍

- 不做大而全知识库。第一版只保留能参与编译判断的知识。
- 不做 AI 自动判定。AI 后续只可用于润色法术卡、生成自然语言解释或帮助检索资料。
- 不做复杂规则 DSL。先用 Python 规则函数，等节点库稳定后再抽象。
- 不追求移动端复杂编辑。图编辑以桌面为主。
- 不把高阶术式做成“强度排行榜”。所有输出必须回到理解深度、场景、代价和可控度。

## 13. 下一步执行顺序

建议立即进入阶段一。

第一批任务：

1. 初始化 `backend`、`data/nodes`、`data/examples`。
2. 定义 Pydantic 模型。
3. 写入最小节点库。
4. 实现节点加载和基础图校验。
5. 实现普通法术编译。
6. 实现结界与祈愿特殊编译。
7. 实现评分和法术卡。
